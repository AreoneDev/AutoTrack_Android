# Android customer mapping

The `codex/lead-mapping` branch starts at `641ee18`, which includes authentication commit `89dc39d`. Authentication uses `AccountSession`; database operations use the account facade returned by `Services.getDataAccess`. Existing uncommitted `sync` files are unrelated and are retained.

## Field contract

`LeadMapper` maps the 19 scalar customer fields to the existing web repository names: `first_name`, `last_name`, `phone`, `lead_email`, `lead_division`, `lead_address`, `lead_city`, `lead_province`, `lead_country`, `lead_postal_code`, `budget`, `stage`, `follow_up_date`, `score`, `notes`, `created_at`, `last_interaction_date`, `last_interaction_by`, and `status`. Mapping does not infer ownership, merge customers by name or phone, or export a local numeric primary key. Missing dates remain null. Invalid dates raise an error rather than becoming today.

Supply an explicit business timezone. The normalized `toRow` representation uses a calendar day for follow-up dates; `toCloudRow`, used by `LeadMappingService`, emits midnight in that timezone as a UTC ISO timestamp for compatibility with the current web repository. A future move to a PostgreSQL `date` column requires coordinated changes to the web reader, writer, and daily queries. Creation and interaction times use UTC ISO timestamps. Postgres fractional seconds are accepted through six digits and truncated to Java `Date` millisecond precision. Existing local `dd/MM/yyyy` values are strictly parsed in the device timezone; their original time and timezone cannot be recovered.

Vehicle interest and trade-in are separate nullable snapshots. They preserve make, model, year, trim, price, color, stock status, VIN, and transmission. Local vehicle IDs are never treated as cloud catalogue IDs. Snapshot conversion validates a four-digit year. No automatic catalogue match is performed: current web relationship rows support only a vehicle reference and trim override and cannot represent every historical snapshot. The synchronization implementation must resolve an unambiguous catalogue reference or retain the snapshot for explicit resolution without discarding its attributes. No cloud relationship tables are changed here.

## Identity contract

`DataAccess.getLeadIdentity(localId)` allocates a UUID once and persists it transactionally before any upload. Reopening the database or retrying returns that UUID. `findLeadIdentity(syncId)` resolves an existing local ID, including a retained identity for a deleted row. `bindLeadIdentity(localId, syncId, cloudId, version)` records an upload acknowledgement or binds a newly inserted downloaded row before a local UUID is allocated. Look up the UUID before inserting a downloaded customer. The synchronization implementation must make remote-row application atomic and handle pending local edits before changing customer fields.

Identity uniqueness is scoped by account. A local ID can map to only one UUID and cloud ID; cloud IDs and UUIDs cannot map to multiple local IDs in that account. Versions cannot move backwards. Cloud IDs remain Java `long` values, including values outside JavaScript's safe integer range. A JSON/web transport must preserve such IDs as exact integers or strings, never round them through a JavaScript number.

`LeadMappingService.prepare(localId)` restores a valid session, reads the customer through the account facade, obtains the persisted identity, and returns immutable scalar and vehicle payloads plus the base version. The scalar payload includes `sync_id`; it excludes `lead_id`, client-written `version`, and `owner_id`. Use server ownership defaults and RLS, UUID idempotency, and a version precondition at the synchronization boundary. `acknowledge` rejects an earlier account/session generation and records the server identity. It does not clear a dirty flag or acknowledge a queue item; an intervening local edit must remain pending.

## Local migration and data retention

Opening a database runs an additive transaction that adds score, interaction fields, an explicit legacy-field knowledge flag, and an identity table. `MappingSchema` records this mapping schema as version 1 without taking ownership of SQLite's application-wide `user_version`. Migration does not rewrite old dates, PII, numeric IDs, or vehicle snapshots. Injected failures roll back the schema additions and retain original rows. Reopening is idempotent. Demo customer and notification seeding is limited to initial customer-table creation and runs in the schema transaction. Deleting all demo rows does not recreate them on reopening, and account databases continue to disable demo seeding.

New customers persist all scalar fields, retain timestamp precision, and can clear either vehicle snapshot. Existing rows retain `MappingFieldsKnown=0`, even after an ordinary local update: score and interaction values were absent from the old schema, so prepared legacy patches omit those three fields rather than overwrite existing cloud data with invented defaults. A future complete remote hydration or explicit field-level migration can establish their provenance. The layer does not automatically import or assign the legacy database to a signed-in account. Owner-bound identity storage requires the matching account database filename.

The existing `CryptoManager` format and fallback behavior are unchanged. Mapping expects already decrypted objects. This work does not establish fail-closed decryption of damaged or unavailable legacy ciphertext; an explicit legacy import must detect and quarantine those cases before uploading. No cloud requests, customer uploads, live schema changes, queue behavior, or conflict resolution are introduced.

## Verification

TDD started with executable failing mapper and service tests using unsupported API shells, then added implementations. SQLite device tests first demonstrated missing identity APIs and loss of the score field, then passed after migration and persistence changes. The initial mapper test's incorrect field count was replaced with an exact expected field-name set; all per-field round-trip assertions were retained.

The local JDK path from the earlier authentication work no longer exists. JDK 25 was incompatible with this Gradle version; verification uses the installed `C:\Users\Lenovo\.jdks\openjdk-21.0.1`. The full JVM suite has 72 passing tests, including 10 mapping tests. Debug application and instrumentation APK builds and Android lint pass. The Gradle connected-test task cannot resolve its offline UTP dependency, so instrumentation runs directly through adb on the connected emulator using the separate debug application ID, UUID-named synthetic account databases, and isolated cache fixtures. No application data clear, production database removal, or cloud credentials are used.

Six mapping device tests cover account isolation, stable identities, large cloud IDs, stale handles, complete field/date persistence, vehicle clearing, old-schema migration, unique remote bindings, retained deletion identities, transactional migration rollback, and refusal to claim a legacy database. The selected regression suite also includes the account database test, real database CRUD suite, storage contract (3 tests), Keystore contract (3 tests), business/persistence seams (7 tests), and customer/notification retention (2 tests).

Final verification passed: all 72 JVM tests and all 23 selected device tests, debug and instrumentation APK builds, Android lint, and the staged whitespace check. The existing sequential-read test was not modified; the retention test only gained an additional notification case.

The two seed regressions were reproduced before fixing production code, retaining every original assertion. `DataRetentionTest.deletedCustomersDoNotReappearAfterReopen` exposed repeated seeding on an empty database; an added notification-retention test failed for the same reason. Initial-table-only transactional seeding fixes both. `BusinessPersistenceSeamTest.testGetSequential` expects Darren/Darryl/Jamie and six records; the synthetic demo now supplies that sequence. Existing customer databases are never rewritten to match the fixture. One early device invocation used incorrect `contract` package names for two regression classes and was corrected. Subsequent runs encountered a stale test activity and were interrupted by concurrent login-preview installations on the shared emulator; device access was coordinated before completing verification. Live Supabase cross-client round trips and RLS remain unverified by this change.
