# Android authentication

The Android app currently supports email and password sign-in. Supply `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` as environment variables, Gradle properties, or entries in the ignored root `local.properties` file when building. Gradle properties take precedence over environment variables and local settings. Sync Gradle in Android Studio after changing the file. Use the project's publishable client key; never put a secret or service-role key in an Android build. The values are embedded in the application and are public. An unconfigured build displays an unavailable message.

`AccountSession` is the authentication boundary for later mapping and synchronization work. Call `restore()` on a background thread to obtain a valid session and rotated token; `current()` is only a snapshot and can expire. Capture `generation()` and check `isCurrent(userId, generation)` before applying asynchronous results. Use the account-scoped `DataAccess` from `Services` and discard it when the account changes. Supabase row-level security remains the server-side authorization boundary.

Each account receives a separate local database. The legacy database is retained and is not automatically assigned to a user. Session storage and local databases are excluded from Android backup and device transfer. The debug application has a separate application ID to protect existing application data during tests.

The session and HTTP contract unit tests use synthetic credentials and mocked transport. On the connected emulator, restarting the app restored an existing independent test session; isolated account database and secure-store device tests passed. The registration UI device test passed using synthetic data and a fake provider; it was added after the initial registration implementation because the earlier TDD coverage was at the provider contract layer. A separate application ID and a unique Gmail alias were used to verify live registration, receipt of the confirmation email, subsequent password login, and session restoration. Two actual on-screen keyboard key taps were verified in an isolated application; an entire registration entered by tapping the software keyboard was not tested. Server-side RLS isolation has not been verified. The confirmation endpoint redirected toward an insecure HTTP destination, which was not followed; review the Auth redirect configuration separately.

Account registration supports email confirmation; confirmation links follow the existing Supabase project redirect configuration. The app does not automatically determine whether an email exists because sign-in errors do not reliably distinguish an unknown account from incorrect credentials. Email-link login, cloud synchronization, and migration of existing local records are not implemented. Signing out records a persistent pending marker before deleting the session key and clearing local storage. A restart with that marker blocks restoration and offers a retry. If persisting the marker itself fails, the app remains locked in the current process but cannot guarantee recovery after restart. A remote revocation failure is shown separately. Device verification of this recovery remains required.
